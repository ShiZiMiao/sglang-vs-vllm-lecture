    第 10 章 选型、演进与前沿¶

    本章目标：把前九章的知识转化为工程决策。你将得到一个可操作的选型框架、几个典型场景的判断，以及两个引擎共同的演进方向与仍待解决的问题。

    先修知识：第 5 章的机制对比、第 6 章的功能矩阵、第 7 章的评测方法。没读透也没关系，本章会回到“业务问题”而不是“技术细节”。

    一句话概括：选型不是选“最强”，而是选“在你的模型、硬件、流量、SLO、团队约束下最合适”的那个。

    给零基础同学：不要一上来就搭集群。先用一个模型、一台机器跑通；再用第 8 章的脚本测自己的 workload；最后才考虑混合部署/PD 分离。

    10.0 先看三个学生项目¶

    理论讲多了容易飘，先看三个具体例子。

    10.0.1 课程作业：单卡 24 GB，7B 模型，多轮对话 Demo¶

    约束：预算一张 4090，目标是演示聊天机器人，请求量很小。

    建议：

    • 先用 vLLM 跑通，模型覆盖广、文档多、出问题容易搜；
    • 如果对话历史很长、前缀共享明显，再试 SGLang，观察 TTFT 是否下降；
    • 不要一上来就上 PD 分离/量化/投机解码，先把 baseline 跑稳。

    10.0.2 实验室 RAG：共享文档 + JSON 输出¶

    约束：多个 query 共享同一批检索文档，输出要求严格 JSON，延迟敏感。

    建议：

    • SGLang 优先：RadixAttention 复用文档前缀，压缩 FSM 保证 JSON 合法；
    • 把文档按内容哈希做缓存键，避免不同租户串用；
    • 压测重点看 TTFT P99 与 JSON 合法率。

    10.0.3 校园 API 平台：多模型、多模态、多租户¶

    约束：几十个模型，包含文本/视觉/embedding，硬件可能有 NVIDIA/AMD。

    建议：

    • vLLM 作为主平台：模型/硬件/池化模型覆盖广；
    • 对少数前缀密集/结构化模型，单独部署 SGLang 并通过网关路由；
    • 先解决统一鉴权、计费、限流，再谈性能优化。

    共同点：先明确“业务约束”，再选引擎；不要反过来“先选引擎，再找场景”。

    10.1 选型的本质：不是选“最强”，而是选“最合适”¶

    推理引擎的选型至少涉及六个维度：

    维度 关键问题 常见权重
    模型 目标模型是否被支持？精度/量化是否可用？ 高
    硬件 GPU 型号、互联、集群规模是否被支持？ 高
    流量 输入/输出长度、前缀共享、到达模式、并发？ 高
    SLO 关注 TTFT 还是 TPOT？P99 要求？ 高
    功能 结构化输出、多模态、LoRA、投机解码、PD？ 中
    工程 团队熟悉度、运维、监控、升级、社区？ 中

    一个常见的错误是只看“峰值吞吐”或“某篇博客的倍数”。生产选型更像多目标优化：

    \[ \text{Score} = \sum_i w_i \cdot \text{score}_i \]

    这个式子就是“加权平均”：

    • \(w_i\) 是第 \(i\) 项的权重，所有 \(w_i\) 加起来等于 1（或 100%）；
    • \(\text{score}_i\) 是你在第 \(i\) 项给某个引擎打的分（例如 1～5 分）；
    • \(\sum_i\) 表示把每一项“权重 × 分数”加起来。

    一个数值例子。假设你给两个引擎打分如下：

    项目 权重 vLLM SGLang
    目标模型支持 20% 4 5
    目标 workload 性能 25% 4 5
    功能匹配 15% 3 4
    硬件/量化支持 15% 5 3
    运维与生态 10% 5 4
    稳定性/版本 10% 4 4
    成本 5% 4 4

    vLLM 加权分：

    \[ \begin{aligned} \text{vLLM} &= 0.20\times4 + 0.25\times4 + 0.15\times3 + 0.15\times5 \\ &\quad + 0.10\times5 + 0.10\times4 + 0.05\times4 \\ &= 0.80 + 1.00 + 0.45 + 0.75 + 0.50 + 0.40 + 0.20 \\ &= 4.10 \end{aligned} \]

    SGLang 加权分：

    \[ \begin{aligned} \text{SGLang} &= 0.20\times5 + 0.25\times5 + 0.15\times4 + 0.15\times3 \\ &\quad + 0.10\times4 + 0.10\times4 + 0.05\times4 \\ &= 1.00 + 1.25 + 0.60 + 0.45 + 0.40 + 0.40 + 0.20 \\ &= 4.30 \end{aligned} \]

    在这个假设下，SGLang 略高。但请注意：

    • 分数是你自己打的，权重也是你自己定的；
    • 如果“目标模型支持”权重更高，或者 SGLang 在你的模型上不支持，结果会反转；
    • 所以要做敏感性分析：改几组权重，看结论是否稳定。如果一改权重就翻转，说明两个引擎差不多，选运维更省心的那个。

    其中分数应来自你自己的 workload 压测，而不是厂商 PPT。

    10.1.1 一个可用的评分卡¶

    项目 权重 vLLM 打分（1-5） SGLang 打分（1-5） 说明
    目标模型支持 20% 先确认模型是否在支持列表
    目标 workload 性能 25% 用第 7 章方法实测
    功能匹配 15% 结构化输出/多模态/LoRA/PD
    硬件/量化支持 15% 你的 GPU 与精度
    运维与生态 10% K8s、监控、网关、团队经验
    稳定性/版本 10% 锁版本、回归测试成本
    成本 5% 每百万 token 的 GPU 成本

    打分时不要“拍脑袋”，每个分数后面写证据（文档链接、压测结果、issue）。

    图 10-1 是一棵可执行的决策树：先排除“跑不了”的硬约束，再比较性能与生态。

    目标模型是否被两个引擎都支持？
├─ 否 → 选支持的那个（长尾模型通常 vLLM 更广）
└─ 是

        └─ 否

                └─ 否

    10.3 典型场景分析¶

    10.3.1 场景 A：SaaS 聊天助手，多租户、长 system prompt¶

    特征：

    • 每个租户有自定义 system prompt / 知识库；
    • 多轮对话，历史不断增长；
    • 输出中等长度（100～500 token）；
    • 关注 TTFT 与 P99。

    判断：前缀共享高，SGLang 的 RadixAttention 有天然优势；若缓存压力大、需要按命中长度排序，可以再开启 LPM 等缓存感知策略（默认 FCFS）。但这个判断有前提：共享前缀要长到值得复用、缓存容量要放得下、模型在 SGLang 的支持列表内；任一条件不满足，先回到实测。多租户还需要缓存隔离（按租户加盐/分实例）。

    建议：

    • 主流量走 SGLang；
    • 若模型种类多、长尾模型多，考虑 vLLM 作为补充；
    • 用 cache-aware router 做会话粘性；
    • 对租户做配额，避免一个大租户挤占缓存。

    10.3.2 场景 B：企业 RAG，检索文档长、输出 JSON¶

    特征：

    • 每次请求拼接多篇文档（共享程度中等）；
    • 输出短，且要求严格 JSON；
    • 延迟敏感（TTFT < 1s）。

    判断：输出短 → 前缀缓存收益被放大；结构化输出要求高 → SGLang 的压缩 FSM/jump-forward 更成熟。

    建议：

    • SGLang 优先；
    • 把文档按内容哈希做缓存键，避免不同租户串用；
    • 对 JSON Schema 做简化，减少 FSM 状态数；
    • 压测时重点看 TTFT P99 与 JSON 合法率。

    10.3.3 场景 C：模型聚合平台，多模型、多硬件¶

    特征：

    • 同时提供几十个模型（Llama、Qwen、Mistral、视觉、embedding）；
    • 硬件可能有 NVIDIA/AMD/其他；
    • 需要统一 OpenAI API、计费、限流。

    判断：模型/硬件覆盖是第一位，vLLM 更合适。

    建议：

    • vLLM 作为主平台；
    • 对少数前缀密集/结构化模型，单独部署 SGLang 并通过网关路由；
    • 用统一网关做模型名到后端的映射；
    • 监控每模型/每租户的 token 成本。

    10.3.4 场景 D：DeepSeek-V3/R1 大规模集群¶

    特征：

    • MoE 模型，专家并行，PD 分离；
    • 关注吞吐与每 GPU 成本；
    • 集群有高速互联（NVLink/RDMA）。

    判断：SGLang 的 DP attention、EP/EPLB、PD 分离有更多开箱案例。

    建议：

    • SGLang 优先；
    • 用 EPLB 平衡专家负载；
    • PD 分离按流量比例扩缩容；
    • 重点压测 decode 吞吐与 P99 ITL；
    • 保留 vLLM 作为备选，避免单点依赖。

    10.3.5 场景 E：边缘/小显存部署¶

    特征：

    • 单卡 16～24 GB，7B/8B 模型；
    • 可能用 4-bit 量化；
    • 并发低，关注单请求延迟与显存。

    判断：量化格式与硬件后端支持是关键，vLLM 覆盖更广；SGLang 也可用，但需确认量化 kernel。

    建议：

    • 先确认目标量化格式在两家都支持；
    • 实测 TTFT/TPOT 与显存峰值；
    • 关闭不必要的 CUDA Graph 捕获尺寸，避免显存浪费；
    • 小模型高 QPS 时关注 CPU 开销。

    10.3.6 场景 F：RL rollout / 批量采样¶

    特征：

    • 同一 prompt 多次采样；
    • 需要高吞吐、前缀共享；
    • 与训练框架（verl 等）集成。

    判断：SGLang 在前缀共享与 rollout 集成上更常见。

    建议：

    • SGLang 优先；
    • 利用 RadixAttention 共享 prompt 前缀；
    • 关注采样参数、logprob 返回、与训练框架的接口；
    • 压测时区分 prefill 与 decode 的吞吐。

    10.4 混合部署与路由¶

    你不需要“二选一”。常见做法是按请求特征路由（图 10-2）：

                     ┌─────────────────────┐
   请求 ────────▶│  Gateway / Router   │
                 │  - 模型名映射        │
                 │  - 租户/配额         │
                 │  - 前缀哈希/会话粘性 │
                 └──────┬───────┬──────┘
                        │       │
         前缀密集/结构化 │       │ 通用/长尾模型
                        ▼       ▼
                  ┌─────────┐ ┌─────────┐
                  │ SGLang  │ │  vLLM   │
                  │ 集群    │ │  集群   │
                  └─────────┘ └─────────┘

    图 10-2　按请求特征路由的混合部署

    路由依据：

    • 模型：某些模型只在某一引擎支持；
    • 前缀哈希：把同一会话/同一文档集的请求路由到同一实例（cache-aware）；
    • 请求类型：结构化输出/短输出走 SGLang，长文创作/多模态走 vLLM；
    • 租户/SLO：付费用户走低延迟池，离线批处理走吞吐池；
    • 灰度：新版本先接 5% 流量，对比 TTFT/TPOT/错误率。

    注意事项：

    • 路由层要维护“实例 ↔ 缓存前缀”的近似视图，否则前缀复用会失效；
    • 会话粘性需要处理实例故障与扩缩容；
    • 两套引擎的指标口径要统一，否则无法比较；
    • 混合部署增加运维复杂度，团队规模小的时候慎用。

    10.5 两个引擎共同的演进方向¶

    从 2023 到 2026，两个引擎在许多方向上“殊途同归”：

    10.5.1 PD 分离（Prefill-Decode Disaggregation）¶

    • 动机：prefill 计算密集、decode 带宽密集，混跑互相干扰；
    • 现状：两家都支持，KV 传输后端逐渐标准化（NIXL、Mooncake 等）；
    • 趋势：从“实验特性”走向“大规模部署标配”，尤其是在长 prompt + 长输出混跑的负载中。

    10.5.2 分层 KV 缓存¶

    • GPU → CPU → 磁盘/远端存储；
    • 动机：长会话、Agent、RAG 的前缀复用跨请求、跨时间；
    • 现状：SGLang HiCache、vLLM 的 offload/connector 生态；
    • 趋势：缓存成为独立的“数据面”，引擎负责调度与一致性。

    10.5.3 投机解码¶

    • EAGLE/EAGLE-3、MTP、n-gram、draft model；
    • 动机：decode 受带宽限制，一次前向多出几个 token 可以摊薄权重读取；
    • 趋势：与训练结合（MTP 头）、与结构化输出结合（确定性片段 jump-forward）。

    10.5.4 低精度与硬件协同¶

    • FP8 在 Hopper/Blackwell 上成为常见的部署选项（是否默认取决于模型、引擎与内核支持）；
    • FP4/NVFP4 在新硬件上探索；
    • KV Cache 量化（FP8）直接降低长上下文带宽；
    • 趋势：量化不再是“后处理”，而是模型发布时就考虑的部署格式。

    10.5.5 编译与图执行¶

    • CUDA Graph、torch.compile、piecewise graph；
    • 动机：CPU launch 开销在小模型/高 QPS 下占比高；
    • 趋势：更多模型被“编译友好”地实现，动态形状处理更成熟。

    10.5.6 大规模 MoE 与 EP¶

    • EP、EPLB、DP attention、all-to-all 优化；
    • 动机：DeepSeek 类模型把 MoE 推向主流；
    • 趋势：专家并行成为与 TP 同等重要的维度，负载均衡从“静态”走向“动态”。

    10.5.7 Agent / RL 工作负载¶

    • 前缀共享（多轮、工具调用、分支）；
    • 结构化输出（JSON、函数调用）；
    • 高并发 rollout；
    • 趋势：推理引擎开始为“程序化使用”优化，而不仅是“单轮聊天”。

    10.5.8 多模态与全模态¶

    • 图像/视频/音频输入；
    • 视觉编码器缓存、输入去重；
    • SGLang 有独立的 SGLang-Diffusion/Omni 方向；vLLM 0.34 也已加入 diffusion 与 speech-to-text 配置，但仍以“多模态理解 + 通用 serving”为主；
    • 趋势：多模态预处理与语言模型执行进一步解耦。

    10.6 仍待解决的问题¶

    1. SLO 感知调度：如何在多租户、混合负载下同时优化吞吐、P99 和公平性？
    2. 缓存安全：前缀缓存可能通过命中时间泄漏信息；多租户隔离与性能如何兼得？
    3. KV 传输标准化：PD 分离/分层缓存的 KV 格式、连接器接口仍不统一。
    4. 异构集群：不同 GPU 型号、互联、量化格式混合部署时的调度与负载均衡。
    5. 弹性与容错：实例故障时如何快速恢复 KV/会话，避免重算雪崩？
    6. 可观测性：如何把 TTFT 分解到排队、prefill、采样、网络各段，并自动定位瓶颈？
    7. 成本与能耗：每百万 token 的成本、每瓦性能，尚未成为标准指标。
    8. Benchmark 标准化：workload、指标、报告方式缺乏共识，导致结论难以比较。

    这些问题也是很好的课程项目/研究方向。

    第 2 周 第 3～5 章；读调度器/KV 管理源码 一份源码笔记与对比表
    第 3 周 第 6～8 章；部署两个引擎并压测 一份对照实验报告

    10.7.2 课程项目¶

    1. 迷你 PagedAttention 模拟器：用 Python 模拟块表、分配、COW、LRU，统计碎片率。
    2. Radix Tree 前缀缓存：实现 match/insert/split/evict，对比块级缓存的命中率。
    3. 调度策略实验：在模拟器中实现 FCFS/LPM/SLO-aware，比较 TTFT/P99/公平性。
    4. 对照压测：用第 8 章脚本，测共享前缀/输出长度/并发对两个引擎的影响，写复现报告。
    5. CPU 开销分析：用 py-spy 分析小模型高 QPS 下的 CPU 热点，尝试优化 detokenize/调度。
    6. 结构化输出对比：同一 JSON Schema，比较两家的吞吐、合法率、尾延迟。
    7. PD 分离模拟：用两个实例 + KV 传输（或模拟传输）分析 prefill/decode 比例对成本的影响。

    10.8 常见误区¶

    误区 1：选型是一次性决定，选完就不能改。
    选型可以随模型、流量、版本、团队变化而调整；先跑通，再根据监控数据迁移，不要一开始就追求“终极架构”。

    误区 2：性能是唯一标准。
    模型支持、硬件、功能、运维、团队熟悉度、成本都重要。一个快 10% 但天天挂的引擎，不如一个慢 5% 但稳定的。

    误区 3：大厂用哪个，我就用哪个。
    大厂的模型、流量、团队、基础设施和你不同。他们的最优解不一定是你的最优解。

    误区 4：混合部署一定更好。
    混合部署能兼得两者优势，但增加网关、路由、监控、故障转移的复杂度。团队小的时候，单引擎更省心。

    误区 5：最新版本一定最好。
    新版本可能有性能提升，也可能引入回归。生产要锁版本、灰度、回归测试；不要盲目追 nightly。

    误区 6：benchmark 赢了就适合我。
    benchmark 的 workload 和你不同。用自己的数据、长度分布、并发和 SLO 测过再决定。

    误区 7：自研引擎更可控。
    自研能定制，但你要自己承担 kernel、调度、KV 管理、模型适配、故障排查的长期成本。大多数团队应该用成熟引擎 + 上层定制。

    10.9 本章小结¶

    • 选型是多目标优化：模型、硬件、流量、SLO、功能、工程，缺一不可。
    • 默认倾向：通用/长尾/多硬件 → vLLM；前缀密集/Agent/RAG/结构化/大规模 MoE → SGLang；最终以自测为准。
    • 混合部署与按前缀/模型路由可以兼得两者优势，但增加运维复杂度。
    • 两个引擎正在收敛：PD 分离、分层缓存、投机解码、低精度、编译、EP、Agent/RL。
    • 仍有许多开放问题：SLO 调度、缓存安全、KV 标准化、异构集群、容错、成本与评测标准。
    • 学完本讲义，你应该具备“读论文—看源码—做压测—做选型”的完整闭环能力。

    用大白话再说一遍：选引擎像选交通工具：去隔壁买菜（小流量、单模型）骑自行车就行；每天通勤 50 公里（高并发、长上下文）才需要汽车；要运货（大规模 MoE/PD）才考虑卡车。先看路程和货物，再看车。

    思考题¶

    1. 用 10.1 的评分卡给你的目标场景打分，并说明每个分数的证据来源。
    2. 为什么“模型支持”在选型中权重很高？如果目标模型只在一个引擎支持，其他维度还有意义吗？
    3. 设计一个混合路由策略：如何识别“前缀密集”请求？如何处理会话粘性与故障转移？
    4. PD 分离在什么流量比例下划算？请用 prefill/decode 的资源需求与 KV 传输成本建模。
    5. 分层缓存（HiCache/offload）在什么情况下会降低性能？请从传输带宽与缓存命中率角度分析。
    6. 如果让你为“多租户 + 前缀缓存”设计安全方案，你会如何防止跨租户信息泄漏？
    7. 选择一个开放问题（如 SLO 调度、KV 标准化），写一份 2 页的研究提案：问题、现状、方法、评估。
    8. 你认为未来 3 年推理引擎最可能被“重构”的模块是哪一个？为什么？
