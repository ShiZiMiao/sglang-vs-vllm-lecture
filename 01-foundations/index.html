    第 1 章 从一次文本生成到推理服务¶

    本章目标：建立 LLM 推理的“物理直觉”。读完本章，你应该能解释为什么推理引擎不是“把模型包一层 HTTP 服务”这么简单，并能手算一个模型的显存账本与理论吞吐上限。

    先修知识：第 0 章 的 token、注意力、GPU 显存。没读也没关系，本章会先复盘关键概念。

    一句话概括：LLM 推理 = 先并行读 prompt（prefill），再逐 token 写答案（decode）；前者吃算力，后者吃显存带宽。

    给零基础同学：本章公式不多，重点是三个问题：为什么分两阶段？KV Cache 为什么占显存？为什么 batch 能提高吞吐？遇到公式先看“一步步算”的表格，不要停在符号上。

    1.1 一次请求的旅程¶

    假设用户在聊天框里输入：

    请用三句话解释什么是 KV Cache。

    从点击“发送”到屏幕上一个字一个字地蹦出回答，系统大致经历了下面四个阶段（图 1-1）：

    用户输入
   │
   ▼
┌─────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ HTTP / API  │──▶│ Tokenizer    │──▶│ Prefill      │──▶│ Decode 循环  │
│ 接收请求    │   │ 文本→token   │   │ 并行处理prompt│   │ 逐token生成  │
└─────────────┘   └──────────────┘   └──────────────┘   └──────┬───────┘
                                                                │
                                      ┌──────────────┐          │
                                      │ Detokenizer  │◀─────────┘
                                      │ token→文本   │
                                      └──────┬───────┘
                                             ▼
                                      流式返回给用户

    图 1-1　一次请求的四个阶段

    可以把整个过程拆成四个阶段。

    1.1.0 先用餐厅类比理解¶

    如果你觉得“HTTP、tokenizer、prefill、decode”这些词太抽象，可以先把它想成一家餐厅：

    推理阶段 餐厅类比 发生什么
    HTTP / API 服务员接单 收到用户请求，记录要吃什么
    Tokenizer 把菜名翻译成厨房能看懂的编号 文本切成 token ID
    Prefill 备菜：一次性把所有食材处理好 并行处理整个 prompt，算出第一道菜
    Decode 一道一道炒菜、上菜 每次生成一个 token，循环很多次
    Detokenizer 服务员把菜名报给客人 token ID 还原成文字，流式返回

    两个关键体验指标也可以这样理解：

    • TTFT：从点菜到第一道菜上桌的时间，主要花在“备菜”（prefill）；
    • TPOT：第一道菜之后，两道菜之间的间隔，主要花在“逐道炒菜”（decode）。

    餐厅的厨房再大，也不可能让“炒下一道菜”和“备整桌菜”完全一样快。理解这一点，就理解了为什么推理引擎要把 prefill 和 decode 区别对待。

    1.1.1 输入处理（服务员接单与翻译菜名）¶

    • Tokenization：把文本切成 token。例如“我喜欢吃苹果”可能被切成 ["我", "喜欢", "吃", "苹果"]，具体取决于 tokenizer。一个 token 大约对应 0.5～1 个英文单词，中文通常 1～2 个汉字一个 token。
    • 多模态预处理（如果输入含图片/音频）：把图像切成 patch，经视觉编码器变成 embedding。
    • 模板拼接：聊天模型需要把多轮消息套进 chat template，加上 system prompt、角色标记等。你可以把它想成“厨房规定每道菜必须附一张标准订单”，不同模型的标准订单格式不同。
    • 参数解析：temperature、top_p、max_tokens、停止词、JSON Schema 等。它们决定“菜要做多辣、做多少、什么时候停”。

    这些工作主要发生在 CPU（多模态编码器可能在 GPU），通常只占端到端延迟的一小部分，但在高并发下会成为不可忽视的 CPU 开销。就像餐厅再快，如果服务员接单、写单很慢，客人还是要等。

    1.1.2 Prefill：把 prompt“读进去”（备菜）¶

    模型一次性处理整个 prompt 的所有 token，计算每一层的 Key 和 Value，并产出第一个输出 token 的 logits。这个阶段叫 prefill（预填充）。

    为什么能“一次性”处理？因为 prompt 的所有 token 已经知道了，注意力虽然要求每个 token 只能看前面的 token，但这并不妨碍把它们排成一个大矩阵一起算。就像备菜时，所有食材都摆在案板上，可以同时切。

    关键特征：

    • 所有 prompt token 可以并行计算，矩阵乘法的形状是“大矩阵 × 大矩阵”（GEMM，通用矩阵乘法）；
    • GPU 的算力利用率高；
    • 计算量随 prompt 长度近似平方增长（注意力部分），也随长度线性增长（投影部分）；
    • 产出并保存所有 prompt token 的 KV Cache，供后续 decode 使用；
    • 用户感知到的第一个 token 延迟（TTFT）主要由这个阶段决定。

    1.1.3 Decode：一个 token 一个 token 地“写”（逐道炒菜）¶

    从第二个 token 开始，模型每次只处理一个新 token，但需要读取此前所有 token 的 KV Cache 来做注意力。这个阶段叫 decode（解码）。

    为什么不能像 prefill 那样一次算很多？因为第 2 个 token 依赖第 1 个 token 的采样结果，第 3 个又依赖第 2 个……生成是串行的。你可以提前准备很多食材，但不能在客人还没点下一道菜时就把下一道炒了。

    关键特征：

    • 每步只生成一个 token（或投机解码时的几个候选 token）；
    • 矩阵乘法的形状退化为“矩阵 × 向量”（GEMV，矩阵乘向量）或“小批量 GEMM”；
    • 需要反复读取整个模型的权重和不断增长的 KV Cache，受显存带宽限制；
    • 必须循环 输出长度 次，且输出长度事先未知；
    • 用户感知到的“字与字之间的间隔”就是 decode 的每 token 延迟（TPOT/ITL）。

    1.1.4 输出处理（报菜名与打包）¶

    采样得到 token ID 后，需要：

    • 去 tokenizer 里查表还原成文本；
    • 处理停止条件（EOS、停止字符串、最大长度）；
    • 处理流式输出、增量 detokenization；
    • 统计用量（prompt tokens / completion tokens）。

    看起来简单，但在每秒数千 token 的吞吐下，detokenization 和 JSON 序列化很容易成为 CPU 瓶颈。一个汉字可能由多个 token 拼成，或者一个 token 只对应半个 UTF-8 字符，所以不能“来一个 token 就立刻 decode 一个字符”，而要缓存不完整的字节。成熟的引擎会把这项工作与 GPU 计算重叠。

    1.2 为什么 prefill 和 decode 是“两种生物”¶

    理解 prefill 与 decode 的差异，是理解所有推理优化（以及 vLLM/SGLang 设计差异）的起点。

    1.2.0 先不用公式：GPU 的两个“瓶颈”¶

    把 GPU 想成一个工厂：

    • 算力（FLOPS）：工厂里有多少工人、每秒能做多少次计算；
    • 显存带宽（GB/s）：仓库门有多宽、每秒能搬多少原料进来。

    prefill 和 decode 的区别，就是“原料够不够工人吃”：

    阶段 一次处理多少 token 读一次权重能服务多少 token 更像谁
    Prefill 整个 prompt（可能几千个） 很多个 工人忙不过来（算力瓶颈）
    Decode 1 个（每条序列） 1 个 仓库门太窄（带宽瓶颈）

    举个具体例子：一个 7B 模型有约 14 GB 的 FP16 权重。

    • Prefill 1000 个 token：这 14 GB 权重读一次，可以参与 1000 个 token 的计算，平均“每读 1 字节做了很多活”，所以工人（算力）是瓶颈；
    • Decode 1 个 token：这 14 GB 权重还是要读一遍，但只服务 1 个 token，平均“每读 1 字节只做了一点点活”，所以仓库门（带宽）是瓶颈。

    这就是“算术强度”的直观含义：每从显存读 1 字节，能做多少次浮点运算。下面再把它写成公式。

    1.2.1 算术强度：每读一字节能做多少次浮点运算¶

    算术强度（arithmetic intensity, AI） 定义为：

    \[ AI = \frac{\text{浮点运算次数 FLOPs}}{\text{需要从显存读取的字节数 Bytes}} \quad [\text{FLOP/Byte}] \]

    GPU 有两个关键上限：

    • 峰值算力 \(F\)（FLOP/s），例如 H100 SXM 的 FP16 张量算力约 \(10^{15}\) FLOP/s 量级；
    • 显存带宽 \(B\)（Byte/s），例如 H100 的 HBM3 带宽约 3.3 TB/s。

    在理想情况下，一个 kernel 能达到的性能是：

    \[ \text{Attained FLOP/s} = \min\left(F,\; B \times AI\right) \]

    这就是 Roofline 模型。当 \(AI\) 低于“脊点” \(F/B\) 时，kernel 受带宽限制；高于脊点时受算力限制。H100 的脊点大约是 \(10^{15} / 3.3\times10^{12} \approx 300\) FLOP/Byte。

    1.2.2 Prefill 为什么是计算密集型¶

    对一个长度为 \(L\)、隐藏维度为 \(d\) 的线性层，输入矩阵是 \(L \times d\)，权重是 \(d \times d\)。要理解 \(2Ld^2\)，不要背公式，直接“逐元素数一遍”。

    先约定口径：本讲义按“一次乘法 + 一次加法 = 2 FLOPs”计数。GPU 的 FMA（乘加融合）指令可能把一次乘法和一次加法合成一条指令，但学术/工程上通常仍按 2 FLOPs 计。也有资料把一次 FMA 算作 1 FLOP，此时数值会减半，比较时只要口径一致即可。

    第一步：输出矩阵有多大¶

    矩阵乘法：

    \[ Y = XW \]
    • \(X\) 的形状是 \(L \times d\)（\(L\) 个 token，每个 token 一个 \(d\) 维向量）；
    • \(W\) 的形状是 \(d \times d\)；
    • 所以 \(Y\) 的形状是 \(L \times d\)。

    也就是说，输出一共有：

    \[ L \times d \quad \text{个元素} \]

    第二步：每个输出元素要做多少次运算¶

    输出矩阵第 \(i\) 行、第 \(j\) 列的元素是：

    \[ y_{i,j} = \sum_{k=1}^{d} x_{i,k} \cdot w_{k,j} \]

    把它展开：

    \[ \begin{aligned} y_{i,j} &= \sum_{k=1}^{d} x_{i,k}\, w_{k,j} \\ &= x_{i,1}w_{1,j} + x_{i,2}w_{2,j} + \cdots + x_{i,d}w_{d,j} \end{aligned} \]
    • 有 \(d\) 次乘法；
    • 有 \(d-1\) 次加法把它们加起来；
    • 合计约 \(2d\) 次浮点运算。

    所以每个输出元素约需 \(2d\) FLOPs。

    第三步：乘起来¶

    \[ \text{FLOPs} \approx (L \times d) \times (2d) = 2Ld^2 \]

    更精确地写是 \(Ld(2d-1) = 2Ld^2 - Ld\)；当 \(d\) 很大时，\(Ld\) 可以忽略，所以记作 \(2Ld^2\)。

    一句话记忆：2 是“乘 + 加”，L 是 token 数，d² 是“每个 token 的 d 维输入 × d 维输出”。
    注意：这里的 2 不是“两层”，也不是“K 和 V”。

    第四步：那 \(2d^2\) 字节的权重和 \(2Ld\) 字节的输入呢¶

    权重 \(W\) 有 \(d \times d = d^2\) 个元素；FP16 每个元素 2 字节，所以：

    \[ \text{权重字节} = 2d^2 \]

    输入 \(X\) 有 \(L \times d\) 个元素；FP16 每个元素 2 字节，所以：

    \[ \text{输入字节} = 2Ld \]

    如果还算上“把输出 \(Y\) 写回显存”，还要再加 \(2Ld\) 字节。本讲义在算算术强度时先只算读取，写成 \(2d^2 + 2Ld\)；把写入也算上会变成 \(2d^2 + 4Ld\)，结论不变。

    第五步：算术强度¶

    \[ AI \approx \frac{2Ld^2}{2d^2 + 2Ld} = \frac{Ld}{d+L} \]

    （分子分母同时约掉 \(2d\)。）

    代入具体数字：取 \(L=4096\)，\(d=4096\)。

    • FLOPs：\(2 \times 4096^3 \approx 1.37 \times 10^{11}\)，即约 137 GFLOP；
    • 读取字节：\(2d^2 + 2Ld = 2 \times 4096^2 + 2 \times 4096^2 \approx 6.7 \times 10^7\) 字节，约 64 MiB；
    • 算术强度：\(1.37\times10^{11} / 6.7\times10^7 \approx 2048\) FLOP/Byte。

    H100 的脊点约 300 FLOP/Byte，2048 远高于它，所以这个线性层是计算受限的，GPU 算力能被吃满。

    反过来看 decode：如果 \(L=1\)（一次只处理一个 token），

    • FLOPs：\(2 \times 1 \times 4096^2 \approx 3.36 \times 10^7\)，约 33.6 MFLOP；
    • 读取字节：权重仍是约 32 MiB，输入只有几 KB；
    • 算术强度：约 1 FLOP/Byte，远低于脊点。

    同一个线性层，\(L=4096\) 时是计算受限，\(L=1\) 时是带宽受限——这就是 prefill 和 decode 的本质区别。

    补充：这里只数了一个线性层。一个 Transformer 层还有注意力矩阵（\(QK^T\)、\(AV\) 等），其 FLOPs 约与 \(L^2 d\) 同量级；当 \(L\) 很大时，注意力项可能超过线性层。但无论哪一项，prefill 的整体算术强度都随 \(L\) 增长，结论不变。

    \(L\) 越大，\(AI\) 越接近 \(d\)（通常几千），远高于脊点。因此 prefill 的大矩阵乘法可以把 GPU 算力吃满。

    1.2.3 Decode 为什么是显存带宽密集型¶

    Decode 每步只处理 1 个 token。对一个参数量为 \(P\) 的模型：

    • FLOPs：约 \(2P\)（这里先忽略注意力部分，只看权重矩阵乘）。为什么？\(P\) 个参数，每个参数要与输入做一次乘法，再累加到输出（一次加法）；“乘 + 加”算 2 FLOPs，所以是 \(2P\)。如果 batch 为 \(B\)，则是 \(2PB\)。
    • 需要读取：全部权重约 \(2P\) 字节（\(P\) 个参数 × 2 字节/FP16），外加 KV Cache。

    于是：

    \[ AI \approx \frac{2P\ \text{次浮点运算}}{2P\ \text{字节权重} + \text{KV 字节数}} \]

    注意分子和分母里的 \(2P\) 含义不同：分子是“\(2P\) 次运算”，分母是“\(2P\) 字节权重”，只是 FP16 下“每个参数 2 次运算、2 字节”恰好数值相同。上下文很短时，KV 项接近 0，所以 \(AI \approx 1\)；上下文很长时，KV 项可能达到几百 MB，\(AI\) 会明显低于 1。这远低于脊点 300。即使用上 3.3 TB/s 的带宽，7B 模型在 batch=1 时的理论上限也只有：

    \[ \frac{3.3\times10^{12}\text{ B/s}}{14\times10^{9}\text{ B/步}} \approx 236 \text{ token/s} \]

    而算力上限对应的时间只有 \(14\text{ GFLOP} / 10^{15}\text{ FLOP/s} = 0.014\) ms，显存读取却要约 4.2 ms。batch=1 时一步只产 1 个 token，所以“236 token/s”也可以读作单请求的 TPOT 下限。99% 的时间在等显存。

    1.2.4 批处理如何改变这一切¶

    如果同时 decode \(N\) 条序列，权重只需读一次，却可以服务 \(N\) 个 token。不过，KV 是每条序列各自的，不能只算一份。

    设：

    • 模型参数量 \(P\)；
    • 每条序列当前上下文长度 \(C\)；
    • 单 token KV 字节数 \(k\)（例如 Llama-3-8B 的 \(k=128\) KiB）。

    则：

    • FLOPs：\(N\) 个 token × 每个 token \(2P\) = \(2PN\)；
    • 读取字节：权重 \(2P\)（只读一次）+ \(N\) 条序列的 KV \(N \cdot C \cdot k\)。

    所以：

    \[ AI_{\text{batch}} \approx \frac{2PN}{2P + N \cdot C \cdot k} \]

    分子随 \(N\) 线性增长，分母里权重是固定的、KV 也随 \(N\) 线性增长。\(N\) 很大时，权重项可以忽略，\(AI\) 趋近于：

    \[ AI_{\text{batch}} \to \frac{2P}{C \cdot k} \]

    这个上限很有意思：它和 batch 无关，只和“模型参数 / 单序列 KV 大小”有关。上下文越长，上限越低。

    这里把每个 token 的 FLOPs 近似成 \(2P\)，忽略了注意力本身随上下文增长的计算。长上下文时注意力项不可忽略，但 decode 的主要瓶颈通常仍是 KV 读取，所以这个近似用来判断趋势已经够用。

    以 7B 模型、假设其 KV 配置与 Llama-3-8B 相同（\(k=128\) KiB）为例：

    上下文 \(C\) 无穷 batch 下的 AI 上限 主要瓶颈
    128 约 835 FLOP/Byte 可能计算受限（需要足够大的 batch）
    512 约 209 FLOP/Byte 仍偏带宽
    4096 约 26 FLOP/Byte 明显带宽受限

    （计算：\(2 \times 7\times10^9 / (C \times 131072)\)。）

    所以在 4K 上下文下，即使把 batch 开到很大，decode 的 AI 也只有 20 多，远低于 H100 的脊点 300。增大 batch 能提高吞吐，但不能把长上下文 decode 变成计算受限——KV 读取才是硬上限。这也解释了为什么 KV 量化、减少 KV 读取、投机解码在长上下文场景如此重要。

    这就是推理引擎的核心矛盾：

    吞吐靠批处理，延迟靠小批量；调度器的任务是在两者之间找平衡。

    维度 Prefill Decode
    一次处理的 token 数 \(L\)（整个 prompt） 1（每序列）
    矩阵形状 大 GEMM GEMV / 小 GEMM
    瓶颈 算力 显存带宽
    算术强度 高（~\(L\)） 低（~1）
    GPU 利用率 高 低
    优化手段 融合 kernel、chunked prefill、并行 增大 batch、KV 量化、投机解码、减少 KV 读取
    影响的指标 TTFT TPOT/ITL、吞吐

    1.3 KV Cache：用显存换计算¶

    1.3.1 没有 KV Cache 会怎样¶

    自回归生成的第 \(t\) 步需要计算：

    \[ P(x_t \mid x_1,\dots,x_{t-1}) \]

    注意力机制中，第 \(t\) 个 token 的 Query 要与前 \(t-1\) 个 token 的 Key 做点积，再对 Value 加权求和。如果不缓存，每一步都要重新计算所有历史 token 的 \(K\) 和 \(V\)：

    • 第 1 步算 1 个 token 的 K/V；
    • 第 2 步算 2 个；
    • ……
    • 第 \(T\) 步算 \(T\) 个。

    总计算量是 \(O(T^2)\)。缓存之后，历史 K/V 只算一次，每步新增 1 个 token 的 K/V，K/V 投影的总计算量降为 \(O(T)\)。代价是需要把 K/V 存在显存里，这就是 KV Cache。

    严格说：这里降的是“K/V 投影”的计算量。注意力本身仍要每步对历史 KV 做加权，总注意力计算仍然与 \(T^2\) 相关；但 decode 的瓶颈通常是读取 KV 的带宽，而不是这部分计算。很多资料把“K/V 不用重算”简写成“复杂度从 \(O(T^2)\) 降到 \(O(T)\)”，你要知道它指的是哪一部分。

    类比：读一本小说时，你不需要每读一页就从头再读一遍；KV Cache 就是你记在脑子里的“前文摘要”。但摘要要占脑容量，上下文越长，占得越多。

    1.3.2 单 token KV Cache 有多大¶

    对采用标准多头注意力（MHA）的模型，每层每个 token 需要存：

    • Key：\(H_{kv}\) 个头 × 每头维度 \(d_{head}\) 个数；
    • Value：同样多。

    因此单 token 的 KV Cache 大小为：

    \[ \boxed{\text{KV}_{\text{per token}} = 2 \times L_{\text{layers}} \times H_{kv} \times d_{head} \times b} \]

    其中：

    符号 含义 对 Llama-3-8B 的取值
    \(2\) Key 和 Value 各一份 2
    \(L_{\text{layers}}\) Transformer 层数 32
    \(H_{kv}\) KV 头数（不是 Query 头数） 8
    \(d_{head}\) 每个头的维度 128
    \(b\) 每个元素的字节数 BF16 = 2

    这个公式为什么长这样？

    1. 每层都要存：每一层都有自己的 K/V，所以乘层数；
    2. 每个 KV 头都要存：多头注意力里，每个头有独立的 K/V，所以乘 KV 头数；
    3. 每个头有 \(d_{head}\) 个数字：所以再乘 head 维度；
    4. K 和 V 各一份：所以最前面乘 2；
    5. 每个数字占 \(b\) 字节：FP16/BF16 是 2 字节，FP8 是 1 字节。

    手算 Llama-3-8B（一步一步来）：

    步骤 计算 结果
    1. K 和 V 两份 2 2
    2. 32 层 2 × 32 64
    3. 每层 8 个 KV 头 64 × 8 512
    4. 每个头 128 维 512 × 128 65,536 个数字
    5. 每个数字 2 字节（BF16） 65,536 × 2 131,072 字节
    6. 换算成 KiB 131,072 / 1024 128 KiB

    所以 Llama-3-8B 每存一个 token 的 KV，就要占 128 KiB。8K 上下文就是：

    \[ 8192 \times 128\text{ KiB} = 1{,}048{,}576\text{ KiB} = 1\text{ GiB} \]

    一条 8K 序列就要 1 GiB，32 条就是 32 GiB。这就是为什么长上下文和大并发会迅速吃光显存。

    例 2：Llama-2-7B（32 层，32 个 KV 头，head_dim=128，FP16）

    \[ 2 \times 32 \times 32 \times 128 \times 2 = 512 \text{ KiB/token} \]

    是 Llama-3-8B 的 4 倍。差别来自 GQA（Grouped Query Attention）：

    • MHA（多头注意力）：每个 Query 头都有自己独立的 K/V，KV 头数 = Query 头数；
    • GQA（分组查询注意力）：把 Query 头分组，每组共享一套 K/V，KV 头数更少。

    类比：32 个学生写报告，MHA 是每人买一套参考书（32 套），GQA 是每 4 人共用一套（8 套）。查询（写报告）还是 32 个人，但参考书（KV）只需要 8 套，显存直接省了 4 倍。Llama-3-8B 让多个 Query 头共享一组 KV 头，把 KV 头数从 32 降到 8。

    例 3：DeepSeek-V3 的 MLA（61 层，KV 压缩维度 512 + RoPE 维度 64，BF16）

    \[ (512 + 64) \times 2 \times 61 = 70{,}272 \text{ B} \approx 68.6 \text{ KiB/token} \]

    注意这里没有乘 2：MLA 缓存的是压缩后的 latent（外加 RoPE 部分），不是传统意义上 K、V 各存一份。

    如果它用 128 个 KV 头的 MHA，单 token 约为 \(2 \times 61 \times 128 \times 128 \times 2 \approx 3.8\text{ MiB}\)。MLA 把 KV Cache 压缩了约 56 倍，这是 DeepSeek 能支持长上下文和大并发的重要原因之一。

    1.3.3 由 KV Cache 引出的核心问题¶

    KV Cache 不是“存下来就完了”，它带来了一连串系统问题：

    1. 分配：每条序列长度不同、动态增长，如何分配显存而不产生碎片？
    2. 共享：多个请求有相同 system prompt，能否共用一份 KV？
    3. 回收：序列结束后，显存如何归还？被谁驱逐？
    4. 预知：生成长度未知，如何避免“预留最大长度”造成浪费？
    5. 并行：多张 GPU 上，KV 放在哪、怎么传？

    vLLM 的 PagedAttention 和 SGLang 的 RadixAttention，本质上是对第 1、2、3 题给出的两种不同答案。第 3、4 章会详细展开。

    1.4 衡量推理服务：四个延迟指标与两个吞吐指标¶

    1.4.1 TTFT（Time To First Token）¶

    从请求到达系统，到客户端收到第一个输出 token 的时间。包含：

    \[ \text{TTFT} = \text{排队} + \text{tokenize} + \text{prefill} + \text{采样} + \text{网络} \]

    TTFT 决定用户“等待回答开始”的体感。对话场景通常要求 P50 在几百毫秒、P99 在 1～2 秒以内；长文档摘要可以放宽。

    把一次输出 5 个 token 的请求画在时间轴上，如图 1-2 所示：

    t0                 t1        t2        t3        t4        t5
│                   │         │         │         │         │
请求到达 ──排队+prefill──▶ 第1个token 第2个     第3个     第4个     第5个
│                   │         │         │         │         │
└──── TTFT ────────┘         └── ITL ──┘
                            └────────── TPOT ──────────────┘
└──────────────────────── E2E ────────────────────────────────────────┘

    图 1-2　TTFT、ITL、TPOT 与 E2E 的时间轴

    • TTFT = t1 - t0：等第一个字；
    • ITL = 相邻两个 token 的间隔（t2-t1、t3-t2……）；
    • TPOT = (t5 - t1) / (5 - 1)：平均每个输出 token 的时间；
    • E2E = t5 - t0：从请求到最后一个 token。

    第一道菜等得久（TTFT），后面上菜快（TPOT/ITL）——这正是餐厅类比里的体验。

    1.4.2 TPOT / ITL（每输出 token 时间）¶

    • TPOT（Time Per Output Token）：平均每个输出 token 的耗时：
    \[ \text{TPOT} = \frac{\text{E2E} - \text{TTFT}}{N_{\text{out}} - 1} \]

    为什么要减 1？因为 \(N_{\text{out}}\) 个 token 之间有 \(N_{\text{out}}-1\) 个间隔；而第一个 token 的时间已经包含在 TTFT 里，所以用“第一个 token 之后的总时间”除以“间隔数”。如果 \(N_{\text{out}}=1\)，分母为 0，TPOT 没有定义（只有一个 token，谈不上“每 token 间隔”）。

    • ITL（Inter-Token Latency）：相邻两个 token 的时间间隔。TPOT 是平均值，ITL 关注分布，尤其是 P99。

    用户感知的“打字速度”由 TPOT/ITL 决定。人类阅读速度约为 10～20 token/s，因此 TPOT 低于 50～100 ms 通常已经“够快”；但在代码补全、实时字幕等场景，P99 ITL 的抖动会很敏感。

    1.4.3 E2E（端到端延迟）¶

    \[ \text{E2E} = \text{TTFT} + \text{TPOT} \times (N_{\text{out}} - 1) \]

    注意 E2E 与输出长度强相关。比较两个系统时，必须固定输入/输出长度分布，否则没有意义。

    1.4.4 吞吐（Throughput）¶

    常见三种口径：

    • 输出 token/s：每秒生成多少 output token；
    • 总 token/s：prompt + output 都算；
    • 请求/s：每秒完成多少请求。

    报告吞吐时必须说明：单卡还是整机、什么模型、什么输入输出长度、什么并发、是否含排队。脱离这些条件的“吞吐提升 10 倍”没有意义。

    1.4.5 Goodput：真正有价值的吞吐¶

    真实服务有 SLO（Service Level Objective），例如“TTFT P99 < 1s 且 TPOT P99 < 100 ms”。Goodput 指单位时间内满足 SLO 的请求数或 token 数。

    一个系统可能吞吐很高，但大量请求超时；另一个系统吞吐略低，却能把 P99 压在 SLO 内。显然后者更有价值。第 7 章会详细讲如何测 goodput。

    1.4.6 Little 定律：并发、吞吐与延迟的关系¶

    对稳定系统：

    \[ L = \lambda \times W \]

    其中 \(L\) 是系统内平均请求数（并发），\(\lambda\) 是到达率（请求/s），\(W\) 是平均停留时间（s）。

    例：每秒到达 10 个请求，平均每个请求耗时 2 秒，则系统平均有 20 个请求在飞。若 GPU 只能同时高效服务 8 个，队列就会不断增长——这就是为什么容量规划不能只看单请求延迟。

    1.5 批处理：从静态到连续¶

    1.5.0 先用餐厅类比理解批处理¶

    假设餐厅只有一张大桌：

    • 静态批处理：凑齐 8 个人才开桌，所有人必须等最慢的人吃完才能一起走；新客人只能在门口等下一桌。
    • 连续批处理：谁吃完谁走，空出的座位立刻让新客人坐下；厨房每一步都按“当前还在吃的人”重新安排。

    显然，连续批处理的座位利用率更高，新客人也不用等一整桌吃完。但餐厅要额外管理“谁吃到哪了、谁的菜还没上、座位怎么回收”——这就是推理引擎的调度与 KV 管理。

    1.5.1 静态批处理的问题¶

    最朴素的做法是攒一批请求，一起送进 GPU，等整批结束后再送下一批（图 1-3）：

    时间 →
请求 A: [Prefill][D][D][D][D][D][D][D]        ← 输出 8 个 token
请求 B: [Prefill][D][D][done]                  ← 输出 3 个 token，之后槽位空闲
请求 C: [Prefill][D][D][D][D][D][done]         ← 输出 6 个 token
         └──────────── 整批必须等最长的 A ────────────┘
下一批: 等待 A 结束后才能开始

    图 1-3　静态批处理的时间线

    三个严重浪费：

    1. 填充浪费：为了组成矩阵，短 prompt 要 padding 到最长 prompt 的长度；
    2. 尾部空闲：短序列提前结束，GPU 槽位空转，直到最长序列结束；
    3. 队头阻塞：新请求必须等整批结束才能进入，TTFT 被拉长。

    1.5.2 连续批处理（Continuous Batching）¶

    核心思想：把调度粒度从“一批请求”降到“一次迭代（一个 decode step）”。每一步都可以：

    • 移除已经结束的序列；
    • 加入 waiting 队列中的新序列；
    • 对正在运行的序列各生成一个 token。

    这就是 2022 年 Orca 系统提出的 iteration-level scheduling，也是今天所有主流引擎的基石（图 1-4）。

    时间 →
请求 A: [P][D][D][D][D][D][D][D]
请求 B:    [P][D][D][done]
请求 C:       [P][D][D][D][D][D][done]
请求 D:          [P][D][D][D][D]...

    图 1-4　连续批处理的时间线

    每一步的 batch 组成都可以不同，GPU 利用率显著提高，TTFT 也不再被整批拖累。

    1.5.3 连续批处理的代价¶

    • 变长 KV：每条序列的 KV 长度不同、动态增长，必须有一种灵活的内存管理机制（→ PagedAttention / RadixAttention）；
    • 调度复杂：每一步都要决定“谁上、谁下、prefill 和 decode 怎么混”；
    • 延迟与吞吐权衡：batch 越大，吞吐越高，但单 token 延迟可能变差；
    • 公平性：长请求可能长期占用资源，短请求被饿死。

    可以说，连续批处理是“需求”，PagedAttention 是“满足需求的内存管理方案”。这也解释了为什么 vLLM 的论文标题把两者放在一起：Efficient Memory Management for Large Language Model Serving with PagedAttention。

    1.6 显存账本：一张 GPU 能塞下什么¶

    部署时最常见的错误是“模型权重能放下就能跑”。实际上显存被至少五部分瓜分。你可以把它想成合租预算（图 1-5）：

    • 模型权重 = 房租，必须先付；
    • 激活/workspace = 水电燃气，平时不多，做饭（prefill）时峰值很高；
    • CUDA Graph/通信缓冲区 = 家具，占一块固定空间；
    • KV Cache = 活动空间，住的人越多、待得越久，占得越大；
    • 碎片 = 押金和边角料，看着没用到，实际上拿不回来。

    “权重放得下”只说明房租付得起，不代表所有客人都住得下。

    ┌──────────────────────────────────────────────┐
│ 1. 模型权重（Weights）                        │
│ 2. KV Cache（动态增长，推理引擎的核心资源）    │
│ 3. 激活值 / 临时 workspace（prefill 峰值）     │
│ 4. CUDA Graph、通信缓冲区、cuBLAS workspace    │
│ 5. 碎片与保留（allocator reserved but unused） │
└──────────────────────────────────────────────┘

    图 1-5　显存账本的五个部分

    1.6.1 权重¶

    \[ M_{\text{weights}} = P \times b \]
    • \(P\)：参数个数（例如 7B 模型 \(P=7\times10^9\)）；
    • \(b\)：每个参数占的字节数（FP16/BF16 为 2，FP8 为 1，INT4 约 0.5）；

    • 两者相乘就是权重总字节数。

    • 7B FP16：\(7\times10^9 \times 2 = 14\) GB；

    • 70B FP16：140 GB（单卡 80 GB 放不下，需要 TP≥2 或量化）；
    • 7B INT4：约 3.5 GB（实际还有 scale/zero-point 开销）。

    1.6.2 KV Cache¶

    \[ M_{\text{KV}} = N_{\text{seq}} \times \text{context length} \times \text{KV}_{\text{per token}} \]
    • \(N_{\text{seq}}\)：同时有多少条序列；
    • context length：每条序列平均有多少个 token（prompt + 已生成）；
    • \(\text{KV}_{\text{per token}}\)：每个 token 的 KV 字节数（前面算过，Llama-3-8B 是 128 KiB）。

    三者相乘，就是 KV Cache 的总字节数。注意这里的 context length 是实际长度，不是模型支持的最大长度；如果按最大长度预留，就会浪费大量显存。

    1.6.3 激活值与 workspace¶

    Prefill 时，中间激活值与“本步 token 数 × hidden size”成正比。长 prompt、大 batch 会让峰值很高。Chunked prefill 的一个重要动机就是限制单步处理的 token 数，从而压低激活峰值，避免 OOM。

    1.6.4 一个 80 GB 卡的例子¶

    以 Llama-3-8B、BF16、80 GB A100 为例：

    项目 估算
    权重 16 GB
    激活/workspace 4 GB
    CUDA Graph / 通信 / 上下文 3 GB
    碎片与安全余量 5 GB
    可用于 KV 约 52 GB

    单 token 128 KiB，则 KV 池约：

    \[ 52 \times 1024^3 / 131072 \approx 425{,}984 \text{ tokens} \]

    这个除法在算什么？

    • 分子 \(52 \times 1024^3\)：52 GiB 换算成字节；
    • 分母 \(131072\)：每个 token 的 KV 字节数（128 KiB = 131072 B）；
    • 相除得到“这些显存能存多少个 token”。

    如果每条请求平均 4K 上下文，理论上可同时容纳约 104 条。实际还要扣除块内碎片、前缀缓存、调度预留，通常会更少。

    这也解释了为什么推理引擎的显存利用率参数（vLLM 的 gpu_memory_utilization、SGLang 的 mem_fraction_static）如此重要：它决定了“权重之外还能拿多少来做 KV 池”。设得太高容易 OOM，设得太低浪费显存。

    1.6.5 显存不够时，先动谁¶

    显存不够时，不要盲目调参数。按“影响大小 + 风险”排序：

    优先级 手段 影响 风险
    1 降低 max_num_seqs / max-running-requests 直接减少并发 KV 吞吐下降
    2 降低 max_model_len / context-length 直接减少单条 KV 长上下文请求被拒
    3 开启/调小 chunked prefill 降低激活峰值 长 prompt TTFT 变长
    4 降低显存利用率参数 给运行时留余量 可用 KV 变少
    5 KV Cache FP8 KV 减半 精度风险
    6 权重量化（FP8/AWQ/GPTQ） 权重减半/更多 精度与 kernel 兼容性
    7 增大 TP 权重和 KV 分摊到多卡 通信开销、成本

    一个经验：先降并发/上下文，再考虑量化。量化的收益大，但引入精度和兼容性风险；并发和上下文是“业务可调”的旋钮。

    1.7 推理引擎必须解决的五个问题¶

    把上面的分析收拢，一个 LLM 推理引擎至少要解决五类问题。后续所有章节都可以挂在这张“问题地图”上：

    # 问题 具体内容 典型技术
    1 KV 内存管理 分配、共享、回收、驱逐、碎片 PagedAttention、RadixAttention、前缀缓存、分层缓存
    2 调度 每步选谁、prefill/decode 如何混、抢占、公平性 Continuous batching、chunked prefill、LPM、优先级
    3 执行 注意力 kernel、采样、CUDA Graph、CPU/GPU 重叠 FlashAttention、FlashInfer、CUDA Graph、torch.compile
    4 分布式 权重切分、KV 切分、通信、PD 分离 TP/PP/DP/EP、NCCL、KV 传输
    5 可编程性 API、结构化输出、多模态、前端语言 OpenAI 兼容接口、XGrammar、SGLang DSL

    vLLM 与 SGLang 的共同点：都建立在 continuous batching 之上，都用 GPU kernel 做分页/变长 attention（paged/varlen attention），都支持 OpenAI API、张量并行、量化、投机解码。

    主要分野：

    • 问题 1：vLLM 用固定大小的块 + 块表 + 哈希前缀缓存；SGLang 用token 级基数树索引 + 底层分页/槽位池 + 引用计数 + LRU。树是索引，KV 仍然要按页或槽位分配，两者不是“分页 vs 不分页”的对立。
    • 问题 2：vLLM 默认 FCFS + token budget；SGLang 默认也是 FCFS，但额外提供 LPM/DFS-weight 等可选的缓存感知策略。注意“SGLang 默认 LPM”是早期版本（如 0.4.0）的说法；0.4.6 起（含 0.5.23）已改为默认 FCFS，需要显式指定 --schedule-policy lpm 才会启用。
    • 问题 5：SGLang 额外提供了一套 Python 内嵌的前端语言，用于表达分支、选择、约束等程序结构；vLLM 更聚焦于通用 serving。

    1.8 常见误区¶

    误区 1：模型权重能放下，服务就能跑。
    不对。权重只占显存的一部分，KV Cache、激活峰值、CUDA Graph、碎片都要占空间。24 GB 卡放 14 GB 的 7B 权重，看起来还剩 10 GB，但 8K 上下文 × 64 并发可能需要几十 GB 的 KV。

    误区 2：batch 越大，吞吐越高，所以越大越好。
    吞吐通常随 batch 上升，但 TPOT/ITL 也会变差，P99 尾延迟更敏感。生产要看 SLO 下的 goodput，而不是单一的“最大吞吐”。

    误区 3：KV Cache 只影响显存，不影响速度。
    KV Cache 既要占显存，又要在 decode 每步被读取。上下文越长，读 KV 的带宽开销越大，TPOT 越容易变差。

    误区 4：TTFT 低就代表服务快。
    TTFT 只衡量“第一个字”，如果输出很长，用户大部分时间在等后面的 token。要同时看 TTFT、TPOT/ITL 和 E2E。

    误区 5：量化一定会明显降智，或者 FP8 一定更快。
    量化是否降智取决于方法、校准数据和任务；FP8 是否更快取决于 GPU 架构、kernel 支持和瓶颈位置。都要实测。

    误区 6：平均延迟能代表用户体验。
    平均值会被少数极慢请求拉高或掩盖。生产更关注 P50/P99，尤其是 P99 尾延迟。

    误区 7：prefill 和 decode 可以用同一套优化。
    Prefill 吃算力，适合大矩阵、chunked prefill、并行；decode 吃带宽，适合大 batch、KV 量化、投机解码。两者目标不同，甚至互相冲突。

    1.9 本章小结¶

    • LLM 推理分为 prefill（并行读 prompt，计算密集）和 decode（逐 token 生成，带宽密集）两个阶段。
    • KV Cache 把历史 K/V 存下来，把 K/V 投影的 \(O(T^2)\) 重算降为 \(O(T)\)，代价是显存；注意力对历史 KV 的加权仍与 \(T^2\) 相关。
    • 单 token KV 大小由层数、KV 头数、head_dim、精度决定；GQA/MLA 能大幅压缩。
    • 核心指标：TTFT、TPOT/ITL、E2E、吞吐、goodput；用 Little 定律做容量规划。
    • Continuous batching 把调度粒度降到每一步，是吞吐提升的关键，但也带来变长 KV 管理问题。
    • 显存账本 = 权重 + KV + 激活 + 运行时开销 + 碎片；KV 池大小决定了最大并发。
    • 推理引擎的五大问题：KV 管理、调度、执行、分布式、可编程性——这就是后续章节的路线图。

    用大白话再说一遍：模型先把 prompt 一口气读进去（prefill），像备菜，费算力；然后一个字一个字往外蹦（decode），像炒菜，费显存带宽。KV Cache 是记下来的“前文笔记”，batch 是“同时炒几桌菜”。推理引擎就是那个既要让厨房不闲着、又要让客人别等太久的调度系统。

    思考题¶

    1. 一个 13B 模型，40 层，32 个 KV 头，head_dim=128，FP16。问：单 token KV Cache 多大？若一张 80 GB 卡留给 KV 50 GB，最多能同时服务多少条 8K 上下文的序列？
    2. 为什么 prefill 阶段 GPU 利用率高，而 decode 阶段低？如果把 batch 从 1 增加到 64，decode 的算术强度如何变化？什么时候会重新变成计算受限？
    3. 某服务每秒到达 20 个请求，平均每个请求耗时 3 秒。系统平均并发是多少？如果 GPU 的最佳并发是 30，会发生什么？
    4. 静态 batching 的三种浪费分别是什么？continuous batching 如何消除它们？又引入了哪些新问题？
    5. 为什么说“模型权重放得下”不等于“服务跑得起来”？请列出一个 7B 模型在 24 GB 卡上部署时可能 OOM 的三个原因。
    6. 假设你把 KV Cache 从 FP16 量化到 FP8，单 token KV 减半。这会如何影响：(a) 最大并发；(b) TTFT；(c) TPOT；(d) 输出质量？请分别讨论。
    7. 用自己的话解释：为什么说 PagedAttention 是“操作系统虚拟内存”思想在 LLM 推理中的复现？
