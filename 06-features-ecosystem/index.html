    第 6 章 功能、模型与生态对比¶

    本章目标：从“能不能用”而不是“原理优不优雅”的角度比较两个引擎。工程选型时，模型覆盖、量化格式、部署集成、运维能力往往比论文里的吞吐数字更能决定成败。

    先修知识：第 1～5 章。本章术语较多，6.0 节会先用大白话解释量化、LoRA、多模态、投机解码、PD 分离。

    一句话概括：vLLM 胜在“广”（模型、硬件、格式、生态），SGLang 胜在“深”（前缀复用、结构化输出、大规模 MoE）。

    给零基础同学：不要被功能矩阵吓到。先问自己三个问题：我的模型支持吗？我的硬件/量化格式支持吗？我需要的功能（结构化输出、多模态、PD）支持吗？其余都是优化项。

    重要说明：本章的功能矩阵按 2026-11（vLLM 0.34.0 / SGLang 0.5.23） 核对。两个项目迭代极快，具体支持情况请以你安装版本的官方文档、--help 和模型支持列表为准。表中 ✅/⚠️/— 表示“主流支持/部分支持或需配置/通常不支持”，不是绝对承诺。

    6.0 五个术语先讲清楚¶

    在看功能矩阵之前，先用大白话解释本章反复出现的五个词。

    6.0.1 量化（Quantization）¶

    模型权重原本用 16 位浮点数（FP16/BF16）存，每个数字占 2 字节。量化就是用更少的位数存：

    • FP8：每个数字 1 字节，显存减半；
    • INT4/AWQ/GPTQ：每个数字约 0.5 字节，显存降到 1/4；
    • KV Cache 也可以量化，长上下文收益更明显。

    类比：把“精确到小数点后 6 位”的账本，改成“保留 2 位小数”。大多数时候够用，但极端情况可能算错。量化是否降智、是否更快，取决于方法、校准数据和硬件 kernel，必须实测。

    6.0.2 LoRA（Low-Rank Adaptation）¶

    LoRA 是给大模型加一个小补丁，只训练很少的参数，就能让同一个基座模型适配不同任务/租户。

    类比：同一本教材（基座模型），给不同班级发不同的“补充讲义”（LoRA adapter）。教材不用重印，讲义很薄，切换成本低。

    多租户平台常用“一个基座 + 多个 LoRA”，但要注意：不同 LoRA 的 KV 不能混用，前缀缓存必须把 LoRA ID 纳入哈希。

    6.0.3 多模态（Multimodal）¶

    让模型同时理解文字、图片、音频、视频。图像通常先被切成 patch，经视觉编码器变成向量，再和文本 token 拼接。

    类比：把图片翻译成模型能读的“另一种 token”。多模态的瓶颈往往在视觉编码器，而不是语言模型本身。

    6.0.4 投机解码（Speculative Decoding）¶

    用小模型/草稿头先猜几个 token，再用大模型一次性验证：

    小模型：我猜接下来是 "快速排序"
大模型：前 3 个 token 对，第 4 个不对 → 接受 3 个，纠正 1 个

    类比：实习生先起草，老板批改。批改比从头写快，但如果实习生猜得太离谱，就白忙。收益取决于接受率。

    6.0.5 PD 分离（Prefill-Decode Disaggregation）¶

    把 prefill（备菜）和 decode（炒菜）放到不同的 GPU 池：

    请求 → [Prefill 池] --KV 传输--> [Decode 池] → 输出

    类比：中央厨房统一备菜，门店只管炒菜。好处是两阶段可以独立扩缩容；代价是要用高速网络搬运“半成品”（KV），架构更复杂。

    6.1 模型覆盖¶

    6.1.1 稠密模型¶

    两家都支持主流开源架构（以下为截至 2026-11（vLLM 0.34.0 / SGLang 0.5.23） 的公开支持情况；新模型发布后请查 vLLM Supported Models 与 SGLang 模型实现目录）：

    • Llama 2/3/3.1/3.2/3.3、Mistral/Mixtral、Qwen 2/2.5/3、Gemma/Gemma 2/3、Phi 系列、Yi、DeepSeek 系列、GLM、InternLM 等；
    • 通过 HuggingFace 配置加载，支持 trust_remote_code；
    • 支持 GQA、RoPE、ALiBi、滑动窗口注意力、MoE 等结构。

    差异主要在长尾模型：

    • vLLM 的模型库与社区贡献更广，新模型/冷门模型通常更早支持；
    • SGLang 对热门模型（Qwen、Llama、DeepSeek、Mistral）优化更深，长尾模型可能滞后。

    6.1.2 MoE 与大模型¶

    • 两家都支持 Mixtral、DeepSeek-V2/V3/R1、Qwen-MoE 等；
    • SGLang 在 DeepSeek 类模型上有更完整的“开箱”方案：DP attention、EP、EPLB、PD 分离、FP8 blockwise；
    • vLLM 也支持 EP/DP 与 DeepSeek，生态集成更通用。

    如果目标是“在 H100 集群上部署 DeepSeek-V3/R1 并压榨吞吐”，SGLang 的默认配置与案例更多；如果是“多模型、多租户、长尾模型统一平台”，vLLM 更稳。

    6.1.3 多模态¶

    能力 vLLM SGLang
    图像理解（LLaVA、Qwen-VL、InternVL 等） ✅ 覆盖广 ✅ 主流模型
    视频理解 ✅ 部分模型 ✅ 部分模型
    音频/语音 ✅ 部分模型 ⚠️ 视模型
    视觉编码器缓存 ✅ ✅
    多模态前缀缓存 ✅（图像哈希参与块哈希） ✅（树匹配 + 多模态哈希）

    vLLM 的多模态覆盖更广；SGLang 在 Qwen-VL 等热门模型上优化较好。多模态的瓶颈通常在视觉编码器与输入预处理，选型时要单独测 encoder 吞吐。

    6.1.4 池化模型（Embedding / Rerank / 分类）¶

    • vLLM 支持 embedding、分类、打分等池化模型，适合统一 serving 平台；
    • SGLang 支持 embedding/rerank 模型（如 --is-embedding），但生态相对窄；
    • 如果业务同时需要生成与 embedding，vLLM 的统一平台属性更方便；如果 embedding 量大且模型固定，专门引擎（如 TEI）可能更划算。

    6.1.5 扩散/全模态（新兴）¶

    2025—2026 年，两家都在向 Diffusion 与语音/全模态扩展：SGLang 有独立的 SGLang-Diffusion 文档与 Omni（TTS/ASR）示例；vLLM 0.34.0 的源码中也已出现 vllm/config/diffusion.py 与 speech_to_text 配置及文档。这些新方向变化快，成熟度因模型而异，选型时应视为“额外选项”，不要作为核心稳定性的依据。

    6.2 量化¶

    量化直接决定显存占用与 decode 带宽，是部署中最常用的优化之一。

    格式 vLLM SGLang 说明
    FP8（W8A8） ✅ ✅ Hopper/Blackwell 友好，精度损失小
    FP8 blockwise ✅ ✅（DeepSeek 常用） 按块缩放，适合大模型
    AWQ（4-bit） ✅ ✅ 权重量化，需校准
    GPTQ（4/8-bit） ✅ ✅ 权重量化，社区格式
    INT8 W8A8 ✅ ✅ 需要 kernel 支持
    INT4 ✅ ✅ 显存受限场景
    GGUF ✅ ⚠️ 部分 社区格式，CPU/混合推理
    BitsAndBytes ✅ ⚠️ 部分 易用，性能一般
    NVFP4 ✅（新硬件） ⚠️ 视版本 Blackwell 的 4-bit 格式
    KV Cache FP8 ✅ ✅ 直接把 KV 减半，影响长上下文并发

    选型建议：

    • 精度优先：BF16/FP16；显存不够再考虑 FP8；
    • 显存受限：AWQ/GPTQ 4-bit；注意精度回归；
    • 长上下文：优先 KV Cache FP8，比权重量化更直接地降低 KV 带宽；
    • 新硬件：FP8/FP4 的 kernel 支持差异大，必须实测。

    两家都支持“量化 + 前缀缓存 + 投机解码”的组合，但组合的兼容性矩阵很复杂，生产前要做回归测试。

    6.3 LoRA 与多租户¶

    能力 vLLM SGLang
    动态加载 LoRA ✅ ✅
    同 batch 多 adapter ✅ ✅
    最大 rank/数量配置 ✅ ✅
    LoRA + 前缀缓存 ✅（LoRA ID 参与哈希） ✅（需注意缓存隔离）
    多租户配额 ⚠️ 依赖上层 ⚠️ 依赖上层

    多租户平台通常需要：

    • 每租户一个 LoRA；
    • 请求级路由到对应 adapter；
    • 缓存按租户隔离（避免前缀串用）；
    • 配额与限流。

    两家都提供基础能力，但“平台级多租户”通常需要在外层网关/控制面实现。

    6.4 结构化输出与约束解码¶

    能力 vLLM SGLang
    JSON Schema ✅ ✅
    正则约束 ✅ ✅
    EBNF/语法 ✅（guided_grammar） ✅（原生 ebnf）
    多选一（choice） ✅ ✅
    压缩 FSM 视后端 ✅
    Jump-forward 视后端 ✅
    语法编译与计算重叠 部分 ✅ 强调
    OpenAI response_format ✅ ✅
    工具调用（tool calling） ✅ ✅

    SGLang 的结构化输出是传统强项，尤其在“复杂 JSON Schema + 高并发 + 短输出”场景；vLLM 通过 xgrammar 也能达到很好效果。若业务强依赖约束解码，建议用同一套 schema 在两家做对照压测。

    6.5 投机解码¶

    方法 vLLM SGLang 适用场景
    Draft model ✅ ✅ 有小模型可配套
    N-gram ✅ ⚠️ 视版本 重复性高的文本
    EAGLE / EAGLE-3 ✅ ✅ 通用加速，需草稿头
    MTP（DeepSeek） ✅ ✅ DeepSeek 系列
    Medusa ⚠️ 视版本 ⚠️ 视版本 多草稿头

    投机解码的收益高度依赖接受率：

    • 代码补全、格式化输出、重复模板：接受率高，加速明显；
    • 开放式创作、高温度采样：接受率低，可能不赚甚至变慢；
    • 草稿模型/头的显存开销要计入账本。

    两家都支持主流的 EAGLE/MTP 路线；具体模型的草稿头可用性不同，选型时要确认“目标模型 + 投机方法”的组合是否被支持。

    6.10 场景化选型矩阵¶

    场景 首选 理由
    通用 OpenAI API 平台，多模型/多租户 vLLM 模型覆盖广、API 标准、生态成熟
    多轮对话/Agent/RAG，前缀高度共享 SGLang RadixAttention + 可选 LPM 缓存感知调度，TTFT 与吞吐占优
    结构化 JSON/正则输出为主 SGLang（略优） 压缩 FSM + jump-forward，成熟度高
    DeepSeek-V3/R1 大规模部署 SGLang（常用） DP attention、EP/EPLB、PD 分离案例多
    长尾模型/新硬件/特殊量化 vLLM 后端与格式覆盖广
    离线批量生成 两者皆可 看模型与吞吐，实测
    RL rollout / 批量采样 SGLang（常见） 前缀共享 + 高吞吐，verl 集成
    Embedding/分类/统一平台 vLLM 池化模型支持更完整
    需要前端 DSL 表达复杂程序 SGLang 原生语言层
    需要成熟 K8s/网关集成 vLLM 生态集成多
    边缘/小显存 两者皆可 看量化与模型支持，vLLM 硬件更广

    注意：这张表是“默认倾向”，不是绝对结论。表中“SGLang 占优”通常还隐含几个条件：共享前缀足够长、缓存容量能容纳、输出不过长、两个引擎版本相近且都做了基本调参。任一条件不成立，差距都可能缩小甚至反转。同一场景下，模型、版本、并发、SLO 变化都可能翻转结果；第 8 章会给出对照实验方法。

    6.11 常见误区¶

    误区 1：功能矩阵里 ✅ 就一定能在我的模型/硬件上跑。
    ✅ 只表示“主流路径支持”；具体模型、量化格式、GPU 架构、kernel 组合都可能有限制。必须看模型支持列表并实测。

    误区 2：量化一定会明显降智。
    FP8 通常损失很小；4-bit 权重量化在部分任务上可能退化。是否可接受取决于业务容差和评测。

    误区 3：LoRA 可以随便和前缀缓存混用。
    不同 LoRA 的权重不同，同一前缀的 KV 可能不同；缓存键必须包含 LoRA ID，否则会串用结果。

    误区 4：多模态只是“多传一张图”。
    图像要经过编码器、投影层、token 拼接，显存与计算开销可能比文本大得多；视觉编码器往往是瓶颈。

    误区 5：PD 分离总是更快。
    PD 分离适合两阶段资源需求差异大、需要独立扩缩容的场景；KV 传输成本高时，混跑可能更划算。

    误区 6：社区大 = 一定更适合我。
    社区大意味着覆盖广、排错容易；但如果你的核心场景是前缀密集/结构化输出，SGLang 可能更合适。选型看匹配度，不看粉丝数。

    6.12 本章小结¶

    • vLLM 的优势是“广”：模型、硬件、量化、集成、池化模型、运维生态。
    • SGLang 的优势是“深”：前缀复用、缓存感知调度（可选）、结构化输出、大规模 MoE/PD。
    • 两家在核心功能上高度重叠：continuous batching、chunked prefill、prefix caching、CUDA Graph、投机解码、TP/PP/DP/EP、PD 分离。
    • 选型应看“你的 workload 是否落在对方的强项上”，而不是看功能清单谁更长。
    • 版本迭代快，生产必须锁版本、做回归、保留降级方案。

    用大白话再说一遍：vLLM 像一家大超市，东西全、什么牌子都有；SGLang 像一家精品店，热门商品（前缀复用、结构化输出、DeepSeek）做得深。先确认“你要的东西有没有”，再比较“谁做得更好”。
