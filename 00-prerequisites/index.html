    第 0 章 预备知识：从“文字接龙”到 GPU 服务¶

    本章目标：把读懂后面十章所需的背景补齐。你不需要会推导 Transformer，也不需要写过 CUDA；只要会一点 Python、知道“向量是一串数字”，就能跟上。

    先修要求：变量、函数、循环；高中数学的概率与向量概念（忘了也没关系，本章会重新解释）。

    阅读建议：这一章不是“可跳过的引言”。后面的 KV Cache、PagedAttention、TTFT 等概念都建立在这里的直觉上。第一遍读不懂公式没关系，先记住类比和结论。

    一句话概括：LLM 是高级“文字接龙”；token 是它眼中的字；注意力是 token 之间的信息交换；GPU 是做矩阵运算的工厂。

    0.1 大语言模型到底在做什么¶

    0.1.1 一句话：高级“文字接龙”¶

    给定前文，模型预测下一个 token 的概率分布。例如输入：

    今天天气真

    模型可能输出：

    候选下一个 token 概率
    好 0.62
    不错 0.18
    冷 0.09
    热 0.06
    其他 0.05

    这些概率加起来等于 1。模型根据概率随机选一个（也可以用“贪心”选概率最大的），把选中的 token 接到句子后面，再预测下一个：

    今天天气真 → 好 → ， → 适合 → 出去 → 走走 → 。

    这就是 自回归生成（autoregressive generation）：

    • “自回归”的意思是：用自己刚才的输出，作为下一步的输入；
    • 一次只前进一步；
    • 输出长度事先不知道，直到模型生成“结束符”或达到最大长度。

    零基础提示：不要把模型想成“数据库查询”。它不是在记忆里找一句现成的话，而是在每一步计算“下一个 token 应该是什么”的概率。数十亿个参数共同决定了这个概率。

    0.1.2 训练与推理：写菜谱 vs 按菜谱做菜¶

    阶段 做什么 类比 本讲义关注吗
    训练（training） 用大量文本调整模型参数 厨师反复试菜，写出一本菜谱 不关注
    推理（inference） 参数固定，回答用户请求 服务员按菜谱做菜、上菜 全程关注

    训练一次可能花费几百万美元、几周时间；推理则要每天每秒服务大量用户。训练关心“模型准不准”，推理关心“快不快、贵不贵、稳不稳”。这两件事的优化方法完全不同，所以我们需要专门的“推理引擎”。

    0.1.3 为什么“一次只生成一个 token”会慢¶

    假设模型生成 500 个 token，就要把模型跑 500 次。每次都要：

    1. 读取模型权重（几 GB 到几百 GB）；
    2. 读取之前所有 token 的中间结果（KV Cache）；
    3. 做矩阵乘法；
    4. 算出下一个 token 的概率。

    如果每次都要重新读一遍全部权重，代价会非常高。后面章节的 continuous batching、KV Cache、PagedAttention、RadixAttention，都是为了把这几步做得更高效。

    0.2 Token：模型眼中的“字”¶

    0.2.1 模型不直接看汉字或字母¶

    模型看到的是一串整数 ID。把文本变成 ID 的过程叫 tokenization（分词），负责这件事的程序叫 tokenizer。

    例如（不同 tokenizer 结果可能不同）：

    "unbelievable"  →  ["un", "believ", "able"]  →  [359, 8721, 501]
"我喜欢吃苹果"   →  ["我", "喜欢", "吃", "苹果"] →  [1234, 5678, 90, 4321]

    token 不等于字，也不等于词。它更像“模型词表里的最小积木”：

    • 常见词可能是一个 token；
    • 生僻词可能被拆成几个 token；
    • 一个汉字可能是一个 token，也可能和旁边的字合并；
    • 英文一个 token 大约对应 0.5～1 个单词；
    • 中文一个 token 大约对应 1～2 个汉字（因 tokenizer 而异）。

    0.2.2 为什么 token 重要¶

    事情 为什么和 token 有关
    计费 API 通常按输入 token + 输出 token 收费
    上下文长度 “8K 上下文”指 8192 个 token，不是 8192 个字
    显存 KV Cache 按 token 数增长
    延迟 prefill 处理 prompt token，decode 每步生成 1 个 token
    吞吐 通常用 token/s 衡量

    小练习：一段 1000 字的中文，大约是多少 token？
    粗略估计：1000～2000 个 token。具体要用对应模型的 tokenizer 计算。不要用“字数”直接当 token 数。

    0.2.3 词表与 logits¶

    模型最后一层会为词表中的每一个 token 打一个分数，叫 logit。词表可能有 5 万～20 万个 token，所以 logits 是一个很长的向量。

    然后经过 softmax，把分数变成概率：

    logits:  [2.0, 1.0, 0.1, ...]
           ↓ softmax
概率:    [0.66, 0.24, 0.10, ...]   总和 = 1（含省略项）

    采样就是按这些概率选一个 token。温度、top-p 等参数，都是在改变这个概率分布的形状。

    0.3 Transformer 的最小直觉¶

    这一节不要求你推导公式。你只需要知道：模型由很多层组成，每层都在更新每个 token 的向量；注意力让 token 之间交换信息；K 和 V 可以被缓存。

    0.3.1 神经网络：一大串“矩阵乘法 + 非线性”¶

    把神经网络想成一个巨大的函数：

    输入 token ID → 查表得到向量 → 一层层变换 → 输出每个 token 的分数
    • 参数（weights）：函数里可学习的数字，训练时调整；
    • 向量（vector）：一串数字，例如 [0.2, -1.3, 0.7, ...]；
    • 矩阵乘法：把向量按规则混合，是 GPU 最擅长的运算；
    • 层（layer）：一组矩阵乘法 + 激活函数，重复几十次。

    一个 7B 模型有约 70 亿个参数；“7B”就是 7 billion。参数越多，模型通常越聪明，但推理也越贵。

    0.3.2 词向量：把词变成一串数字¶

    模型先把每个 token 变成一个向量，叫 embedding。你可以把它想成“这个词的特征表”：

    "猫"   → [0.8, -0.2, 0.1, ...]
"狗"   → [0.7, -0.1, 0.2, ...]
"汽车" → [-0.5, 0.9, -0.3, ...]

    向量之间的“距离”可以表示语义相似度。模型通过多层变换，让这些向量逐渐带上上下文信息。

    0.3.3 注意力：让 token 互相“开会”¶

    注意力机制要解决的问题是：

    当前这个 token，应该从前面哪些 token 那里获取信息？获取多少？

    它用三个向量来描述每个 token：

    名称 含义 开会类比
    Query（Q） 我想找什么信息 我提出的问题
    Key（K） 我能提供什么标签 每个人名片上的关键词
    Value（V） 我实际能提供的内容 每个人带来的资料

    计算过程可以粗略理解为：

    1. 当前 token 的 Q 和每个历史 token 的 K 做点积，得到“匹配分数”；
    2. 分数经过 softmax，变成“注意力权重”；
    3. 用权重对所有历史 token 的 V 加权求和；
    4. 得到当前 token 的新向量。

    公式长这样，但第一遍不用记：

    \[ \text{Attention}(Q,K,V) = \text{softmax}\left(\frac{QK^T}{\sqrt{d}}\right)V \]
    符号 读法 直观含义
    \(QK^T\) Q 乘 K 的转置 每个 query 和每个 key 的相似度
    \(\sqrt{d}\) 根号 d 防止数值太大，让 softmax 更稳定
    softmax — 把分数变成总和为 1 的权重
    乘 \(V\) — 按权重把资料汇总起来

    零基础提示：你不需要会手算注意力。只要记住：Q 是“我要找什么”，K 是“我有什么标签”，V 是“我有什么内容”。后面讲 KV Cache 时，K 和 V 会被存起来复用。

    0.3.4 因果掩码：不能偷看答案¶

    生成是逐 token 的。预测第 3 个 token 时，模型只能看第 1、2 个 token，不能看第 4 个及以后（因为那些还不存在）。

    实现上用一个 causal mask（因果掩码）：把“未来位置”的注意力分数设为 \(-\infty\)，softmax 后权重为 0。

           看得到吗？
token1  ✓
token2  ✓ ✓
token3  ✓ ✓ ✓
token4  ✓ ✓ ✓ ✓

    这也是为什么生成必须从左到右、一个接一个。

    0.3.5 多头注意力与 MLP¶

    • 多头注意力（multi-head attention）：同时用多组 Q/K/V，从不同角度关注信息，像开多个小组会；
    • MLP（前馈网络）：对每个 token 的向量单独做变换，增加非线性；
    • 残差连接 + LayerNorm：让深层网络更容易训练，暂时理解成“给信息留一条捷径”；
    • 层数：7B 模型通常有 28～32 层，70B 模型有 80 层左右。

    0.3.6 为什么会有 KV Cache¶

    注意力的关键观察：

    • 生成第 \(t\) 个 token 时，需要前面所有 token 的 K 和 V；
    • 前面 token 的 K、V 一旦算出来，不会因为后面生成新 token 而改变；
    • 所以可以把它们存起来，下次直接读，不用重算。

    这就是 KV Cache。如果不缓存，生成第 \(t\) 个 token 时要把前面 \(t-1\) 个 token 的 K/V 全部重算一遍，生成 \(T\) 个 token 的 K/V 投影总工作量是 \(O(T^2)\)；缓存之后，历史 K/V 只算一次，每步只算新 token 的 K/V，K/V 投影总工作量降到 \(O(T)\)。代价是这些 K/V 要占显存。（注意力本身仍要对历史 KV 做加权，和 \(T^2\) 相关；这里说的是省掉重复的 K/V 投影。）

    类比：你读一本小说，不需要每读一页就从头再读一遍。KV Cache 就是你记在脑子里的“前文笔记”。但笔记要占脑容量，上下文越长，占得越多。

    0.4 GPU、显存与“两个瓶颈”¶

    0.4.1 CPU 与 GPU 的分工¶

    CPU GPU
    核心数 少（几十个） 多（成千上万个）
    单核能力 强，适合复杂逻辑 弱，适合简单并行运算
    擅长 分支、控制、串行任务 矩阵乘法、向量运算
    在推理中的角色 请求处理、调度、tokenize 模型前向、注意力、采样

    模型前向本质上是大规模矩阵乘法，所以主要跑在 GPU 上。CPU 负责“把请求准备好、把结果发回去”。

    0.4.2 显存里放了什么¶

    GPU 的显存（HBM）主要放四类东西（图 0-1）：

    ┌─────────────────────────────────────┐
│ 1. 模型权重（固定，几 GB～几百 GB）   │
│ 2. KV Cache（动态，随上下文增长）     │
│ 3. 激活值/临时草稿纸（前向时产生）     │
│ 4. CUDA 上下文、通信缓冲区、碎片       │
└─────────────────────────────────────┘

    图 0-1　GPU 显存的四类占用

    如果显存不够，服务就启动不了，或者运行中 OOM（Out Of Memory）。这四类占用就是第 1 章“显存账本”的雏形。

    0.4.3 算力与带宽：两个不同的上限¶

    • 算力（FLOPS）：GPU 每秒能做多少次浮点运算，像“有多少工人”；
    • 显存带宽（GB/s）：GPU 每秒能从显存读多少数据，像“仓库门有多宽”。

    一个任务可能受算力限制，也可能受带宽限制：

    阶段 主要瓶颈 类比
    Prefill（读 prompt） 算力 很多工人同时处理一大堆材料
    Decode（逐 token 生成） 显存带宽 工人很强，但每次只能从窄门搬一点材料

    这就是为什么：

    • prefill 阶段 GPU 利用率高；
    • decode 阶段 GPU 利用率低，常常在“等显存”；
    • 增大 batch 可以摊薄权重读取，提高吞吐，但会增加延迟。

    0.4.4 常用单位¶

    单位 含义 典型使用场景
    1 KB（SI） 1000 字节 厂商标称、网络带宽
    1 KiB 1024 字节 操作系统、nvidia-smi、引擎日志
    1 MB / 1 MiB 1000 KB / 1024 KiB 约一百万字节
    1 GB / 1 GiB 1000 MB / 1024 MiB 约十亿字节

    KB 在口语里常被用来指 1024 字节，但严格写法是 KiB。本讲义为了直观，GB/GiB 不逐字区分；做显存账本时要注意：模型权重的“14 GB”是十进制，而 nvidia-smi 显示的 MiB 是二进制，直接相减会有约 7% 的偏差。

    0.5 推理服务的四个基本量¶

    0.5.1 延迟、吞吐、并发、成本¶

    用餐厅类比：

    指标 餐厅类比 技术含义
    延迟（latency） 从点菜到吃上第一口的时间 一个请求要等多久
    吞吐（throughput） 每小时能服务多少桌 单位时间处理多少 token/请求
    并发（concurrency） 同时有几桌在吃 系统里同时有多少请求
    成本（cost） 每桌菜的原料和人工 每百万 token 的 GPU 费用

    这四个量互相牵制：

    • 同时开很多桌（高并发）→ 吞吐高，但每桌等得久（延迟高）；
    • 只服务一桌（低并发）→ 延迟低，但吞吐低、成本高；
    • 所以推理引擎的核心工作之一，是在吞吐和延迟之间找平衡。

    0.5.2 Little 定律：并发、吞吐、延迟的关系¶

    对稳定系统：

    \[ \text{并发} = \text{到达率} \times \text{平均延迟} \]

    例：每秒到达 10 个请求，每个请求平均耗时 2 秒，那么系统里平均有：

    \[ 10 \times 2 = 20 \text{ 个请求在飞} \]

    如果 GPU 只能高效服务 8 个请求，队列就会越来越长，延迟继续上升。这就是为什么容量规划不能只看“单请求多快”。

    0.5.3 平均值会骗人：P50 与 P99¶

    假设 100 个请求里，99 个耗时 100 ms，1 个耗时 10s：

    99 个请求：100ms
 1 个请求：10,000ms
    • 平均值：\((99 \times 100 + 10000) / 100 = 199\) ms，被那个慢请求拉高了；
    • P50（中位数）：100 ms，代表“典型体验”；
    • P99：表示“99% 的请求不超过这个值”。按最近秩计算，P99 仍然是 100 ms；那个 10s 的请求属于最慢的 1%，要看 P99.9 或最大值才能看到它。

    所以：

    P99 不是“最慢请求”，也不是“最慢 1% 的平均值”，而是一个分位阈值。

    生产系统通常同时看 P50 和 P99：P50 看常规体验，P99 看尾延迟的边界；如果极端尾部很重要，再加 P99.9 和最大值。不同压测工具对分位数的插值算法可能略有差异，报告时要说明口径。

    0.5.4 SLO：服务目标¶

    SLO（Service Level Objective） 是对服务的量化承诺。例如（TTFT 是首个 token 的延迟，TPOT 是后续每个 token 的延迟，下一节会展开）：

    TTFT P99 < 1 秒
TPOT P99 < 100 毫秒
错误率 < 0.1%

    后面会学到 goodput：不是“总共处理了多少”，而是“有多少请求真正满足了 SLO”。

    0.6 一次请求的端到端旅程（先看地图）¶

    一次请求从进入到流式返回的完整链路如图 0-2 所示。

    用户输入
   │
   ▼
HTTP 请求 ──▶ Tokenizer ──▶ Prefill ──▶ Decode 循环 ──▶ Detokenizer ──▶ 流式返回
   (CPU)        (CPU)        (GPU)        (GPU, 多步)       (CPU)          (网络)

    图 0-2　一次请求的端到端旅程

    阶段 做什么 主要硬件 用户感知
    HTTP 接收请求、鉴权、解析参数 CPU 几乎无感
    Tokenize 文本 → token ID CPU 很短
    Prefill 一次处理整个 prompt，产出第一个 token GPU TTFT（首个 token 延迟）
    Decode 逐 token 生成，直到停止 GPU TPOT/ITL（每 token 延迟）
    Detokenize token ID → 文本，流式输出 CPU 字逐渐出现
    网络 SSE/JSON 返回 网络 受带宽/延迟影响

    类比：点菜（HTTP）→ 备菜（prefill）→ 一道一道上菜（decode）→ 服务员报菜名（detokenize）。第一道菜等得久，后面上菜快，因为厨房已经进入状态。

    0.9 本章自测¶

    1. 用一句话解释“自回归生成”。
    2. token 和汉字/单词有什么区别？为什么计费按 token？
    3. 注意力里的 Q、K、V 分别代表什么？用开会类比说明。
    4. 为什么生成第 3 个 token 时不能看第 4 个 token？
    5. KV Cache 省下了什么计算？代价是什么？
    6. 为什么 decode 阶段容易受显存带宽限制，而 prefill 更容易受算力限制？
    7. 每秒到达 20 个请求，平均延迟 1.5 秒，系统平均并发是多少？
    8. P50 和 P99 分别代表什么？为什么不能只看平均值？

    参考答案¶

    1. 模型根据已生成的 token，预测下一个 token，并把结果接回输入，循环生成。
    2. token 是 tokenizer 词表中的最小单位，可能是一个字、半个词或几个字；计费、上下文和 KV 都按 token 计算，所以按 token 而不是按字数。
    3. Q 是“我想找什么”，K 是“我有什么标签”，V 是“我有什么内容”；用 Q 和 K 的匹配度给 V 加权。
    4. 因为生成是因果的，第 4 个 token 还不存在；训练/推理时用 causal mask 屏蔽未来位置。
    5. 省下了对历史 token 的 K/V 重复计算；代价是显存占用，上下文越长占用越大。
    6. Decode 每步只处理 1 个 token，计算量小，但要把权重和 KV 从显存读出来，所以受带宽限制；prefill 一次处理很多 token，矩阵乘法大，受算力限制。
    7. \(20 \times 1.5 = 30\) 个并发。
    8. P50 是第 50 百分位（中位数），P99 是第 99 百分位（99% 的请求不超过它）；P99 不是“最慢请求”，也不是“最慢 1% 的平均值”。平均值会被少数极慢请求拉高，不能反映大多数用户体验。

    0.10 本章小结¶

    • LLM 做的是“给定前文，预测下一个 token”，并循环生成。
    • 文本先被 tokenizer 切成 token；上下文长度、计费、KV 都按 token 算。
    • Transformer 由多层“注意力 + MLP”组成；注意力用 Q/K/V 让 token 交换信息。
    • 历史 token 的 K/V 可以缓存，这就是 KV Cache；它省计算但占显存。
    • GPU 推理有两个瓶颈：算力（prefill）和显存带宽（decode）。
    • 服务指标不只有“快”：还有吞吐、并发、成本、P50/P99 和 SLO。
    • 后面的所有机制，都可以放回“内存、调度、执行”三条主线中理解。
